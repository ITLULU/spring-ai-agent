# Agent 学习路径评审与调整建议

> 评审日期：2026-10-10 ｜ 环境核查：JDK 21.0.7 ✅ / Maven 3.9.10 ✅ / Docker ❌（影响 Milvus）

## 一、总体判断

路径主体方向正确，三个阶段的选题（生产级 RAG → 企业流程 Agent → 面试包装）符合 2026 年市场对"Java + AI 工程"复合背景的期望。**但存在 4 个结构性风险和 3 个执行层面的坑**，不修正会导致 12 周后"有项目、没深度"。

## 二、逐阶段评审

### 阶段 1（RAG 生产化）——评分：8.5/10

**做对了的：**
- 切块策略对比 + 混合检索 + Rerank 是 Demo 与生产级的真正分水岭，选点准确
- "评测先行"（RAGAS / LLM-as-Judge + 量化数字）是整个路径里最有价值的一条，90% 候选人做不到
- 引用溯源、拒答机制直接对应面试中的幻觉治理追问

**风险与修正：**

| # | 问题 | 建议 |
|---|------|------|
| 1 | **框架二选一选 Spring AI 还是 LangChain4j 没有决策依据**——两者 API 哲学不同（Spring 生态一致性 vs 更完整的链路抽象），周计划前必须先定 | 建议 **Spring AI**：简历上"Spring Boot + Spring AI"对 Java 岗 JD 匹配度最高；LangChain4j 作为面试口头对比项准备即可 |
| 2 | **Milvus 需要 Docker**，当前机器未安装。若第一周被环境问题卡住，节奏会崩 | 脚手架设计为**双后端**：默认内存向量库（SimpleVectorStore，零依赖即可跑通全链路），Milvus 作为 profile 切换。先跑通评测闭环，再上 Milvus |
| 3 | Rerank 模型 bge-reranker 本地部署需要 GPU；无 Docker、大概率无本地 GPU | 两条腿：调用硅基流动/GPUStack 等托管 API（免费额度够开发期用）+ 代码里把 Rerank 抽象成接口，本地 TEI 部署写 docker-compose 留给有 GPU 后 |
| 4 | "50~100 条测试集"由谁构造没说清——**自己手编 QA 对会不自觉贴合系统强项，评测数字虚高，面试被戳穿** | 测试集构造方法要写进计划：以文档段落为单位反向出题（先选段落再出题，保证可溯源），人工只审校不主写；留 20% 做"答案不在库中"的拒答测试题 |

### 阶段 2（Agent 项目）——评分：7.5/10

**做对了的：**
- 选"企业流程类 Agent"而非闲聊/玩具 Demo，选"工单处理"或"数据分析"都在高频场景内
- "把 Agent 做成可控工作流而不是裸调模型"——这是 Java 背景候选人最大的差异化，定位非常准
- MCP、human-in-the-loop 确实是 2025-2026 面试关键词

**风险与修正：**

| # | 问题 | 建议 |
|---|------|------|
| 5 | **两个二选一（工单 vs 数据分析）拖到阶段 2 才决策是错的**——数据分析 Agent 需要库表样本 + 图表渲染，工程量比看起来大 | 建议选**工单智能处理 Agent**：状态机/工作流是它的灵魂，正好吃你的 Java 功底；且能复用阶段 1 的 RAG（工单知识库检索作为一个工具），两阶段项目形成串联而非割裂 |
| 6 | MCP 只被列为"覆盖"项，但 2026 年面试官问 MCP 会问到协议层（tools/resources/prompts 三类原语、stdio vs streamable HTTP） | 工单 Agent 至少把**一个能力（如工单查询）实现为 MCP Server**，其余用 Function Calling——这样两种机制都有实操对比可讲 |
| 7 | 失败重试与人工审核兜底容易做成"写在 README 里但没跑通" | 状态机必须显式建模：`AUTO_RESOLVED / PENDING_HUMAN / FAILED / RETRYING`，用数据库表持久化会话与工单状态，面试能画出状态转移图 |

### 阶段 3（补短板 + 包装）——评分：7/10

| # | 问题 | 建议 |
|---|------|------|
| 8 | **LoRA 微调放在最后一周风险高**——GPU 租用、环境、显存 OOM 任何一个都可能吃掉 3 天 | 微调 Demo 挪到阶段 2 与阶段 3 之间做（第 7-8 周有空档），且只承诺"跑通流程 + 看懂 loss 曲线"，不承诺效果 |
| 9 | Transformer/Attention "讲得清"标准太模糊 | 给出验收锚点：能在白板上画出 Q/K/V 计算流程并解释"为什么 KV Cache 能省计算"、"上下文窗口变长为什么成本平方涨"。达不到就是没达标 |
| 10 | 系统设计题只列了两道 | 至少准备 4 道：知识库系统、客服机器人（幻觉+成本控制）、**RAG 系统的评测与迭代闭环**、**Agent 工作流的可靠性设计**——后两道是你两个项目的自然延伸，性价比最高 |

## 三、路径整体缺口（原文没有的）

1. **缺贯穿的原理线**：阶段 1/2 全是"做"，阶段 3 才"补概念"。建议从第 1 周起每周配 2h 原理学习（与当周实践挂钩：本周做切块→本周读 embedding 原理；本周做 Rerank→本周读 cross-encoder vs bi-encoder），而不是攒到最后。
2. **缺成本意识模块**：2026 面试高频追问"token 成本怎么控"。应在阶段 1 就记录每次评测的 token 消耗与耗时（脚手架已内置统计），阶段 3 包装成"效果-成本权衡"叙事。
3. **"每周精读开源项目"没有验收物**：精读必须落产物——每周一篇 200 字笔记（问题是什么/方案是什么/我的项目能不能借鉴），否则第三周就流于形式。
4. **没有缓冲周**：3×4 周排得太满。周计划里每阶段末尾留 3 天缓冲，用于补漏 + 写 README + 整理面试话术。

## 四、结论

- 路径保留原三阶段结构，按上表 10 条微调。
- 关键决策定死：**Spring AI（非 LangChain4j）；工单 Agent（非数据分析 Agent）；先内存向量库跑通评测闭环，第 3 周再切 Milvus**。
