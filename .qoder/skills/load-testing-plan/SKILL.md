# 压测与容量验证方案（Load Test Plan）

> 核心信条：**先推算，后压测。** 压测的目的是验证静态推算的断裂点是否预测准确，
> 而不是"跑一遍看看行不行"。没有预测的压测只是表演。

## Step 1 — 输入采集（缺失必问）

| 输入 | 必需 | 缺失时 |
|------|------|--------|
| 被测接口清单与 RT 特征（同步/异步、读/写） | ✅ | 读代码 Controller/RPC 层自行梳理，标注 [推断] |
| 目标 QPS 档位 + P99 RT 目标 | ✅ | AskUserQuestion 询问（十万/百万/千万三档） |
| 压测环境资源清单（机型/核数/内存/实例数） | ✅ | 询问；**禁止用生产规格默认压测环境** |
| 生产环境资源与流量现状文档 | 已上线项目 | 沿用 `expert-review-meeting` 的输入闸门规则 |
| 数据现状（表行数、缓存容量、索引体积） | ✅ | 读 schema + 询问增长速率 |

⚠️ 环境折算纪律：压测环境规格 ≠ 生产时，所有结论按 `核数比` 折算并显式写出折算过程；
压测流量会与数据流量（批量入库/评测跑批）抢资源时必须隔离，写进方案前置条件。

## Step 2 — 静态推算（压测前的预测，产出"预期断裂点"）

读代码完成三件事，输出《预测表》——这是本 skill 与"随便写个压测脚本"的分界线：

1. **单实例理论上限**（写算式）：
   ```
   线程池上限 = server.tomcat.threads.max / P99_RT(s)
   CPU 上限   ≈ 核数 / 单请求CPU秒（LLM/检索类按外部等待占比修正）
   连接池上限 = DB池大小 / 每请求DB次数
   下游上限   = 模型API/RAG/第三方限流配额（最常被漏算！）
   单实例QPS  = min(以上)；集群上限 = 单实例 × 实例数 × 0.7（冗余系数）
   ```
2. **找串行点与共享点**：全局锁、单线程 executor、O(N) 重建、文件追加写、
   本地内存索引（扩容正确性问题）、缓存击穿路径——每个标注"预计在第 X 档死于此处"；
3. **数据规模敏感性**：当前数据量 ×10 / ×100 时哪些操作从毫秒变秒（全表加载、无分页、无索引查询）。

《预测表》模板：`| 组件 | 预测瓶颈 | 预测断裂QPS | 验证场景 |`——每个预测必须被 Step 3 的某个场景覆盖。

## Step 3 — 场景设计（五类，按需取用）

| 场景 | 目的 | 压力模型 | 通过判据 |
|------|------|----------|----------|
| S1 基线 | 单实例容量标定 | 阶梯 1→N 递增找拐点 | 拐点≥预测值×0.8（验证推算可信） |
| S2 峰值 | 目标档位达标 | 目标QPS×(读1写1混合) 恒定 30min | P99≤目标、错误率<0.1%、无饱和累积 |
| S3 突增 | 冷启动/扩容能力 | 0→目标QPS 秒级打满（含缓存空态） | 无雪崩、恢复时间<X min |
| S4 浸泡 | 泄漏与累积病灶 | 50%目标QPS 持续 2~4h | 内存/GC/连接数曲线平稳 |
| S5 故障注入 | 降级路径真实性 | 峰值下拔依赖（DB从/缓存/rerank/模型API） | 降级标志生效、无 5xx 风暴、恢复后自愈 |

场景细则与混合流量配比方法见 [TOOLS.md](TOOLS.md)。
**AI/LLM 类项目专项**：token 消耗速率与费用上限要做预算熔断验证；embedding/推理接口限流
往往是第一断裂点，S2 必须单独对模型通路打满一次。

## Step 4 — 工具选型（给默认，留逃生门）

- 默认 **k6**（脚本即代码、压测机自身开销低、Prometheus 出口现成）；
- 团队已有 JMeter 资产 → JMeter（非GUI模式 `jmeter -n -t plan.jmx`，GUI 压测是伪科学）；
- 单接口快速标定 → wrk/wrk2（注意 wrk 的 coordinated omission，要恒定到达率用 wrk2/openrd）；
- 百万级以上 → 多压测机分布式（k6 分片 / Gatling 集群），**先算压测机自身瓶颈**：
  `单压测机上限 ≈ 核数×2000 并发连接`，压测机瓶颈误判为被测系统瓶颈是新手第一坑。

脚本骨架、参数与常见坑：[TOOLS.md](TOOLS.md)。

## Step 5 — 观测先行（无监控不开压）

压测前必须就位，否则压完拿不到归因数据：
- 服务端：QPS/RT 分位/错误率/线程池与连接池使用率/GC 暂停/DB 慢查询，秒级采样；
- 压测侧：到达率（arrival rate）与实际完成率的差值——**到达率塌了说明链路在排队而非在失败**；
- 预案：`jstack/arthas/async-profiler` 在拐点区间抓 CPU 火焰图与阻塞点，压后分析。

## Step 6 — 执行阶梯与熔断纪律

```
1% → 10% → 50% → 100% → 120%（目标QPS），每级 ≥10min
每级出口条件：P99 与错误率达标才升级；
熔断线（立即停压）：错误率>5% 持续1min / 线程池连接池打满 / DB主从延迟>阈值 / 费用触顶
```
压测顺序：S1 → S2 → S5 → S3 → S4（先证容量，再证韧性，浸泡放最后防环境被拖垮）。

## Step 7 — 瓶颈定位方法论（拐点区间二分 + 四类分诊）

拐点处按此顺序排除（每步都有明确观测证据，禁止跳步猜）：
1. **CPU**：us%>85% 或 GC 暂停占比 → 计算瓶颈/序列化/正则回溯，火焰图定位；
2. **排队/锁**：CPU 低但 RT 高、线程 WAITING/BLOCKED 堆积 → 找全局锁、单线程段、同步远程调用；
3. **连接/池饱和**：池等待时间>获取时间 → DB/HTTP 池过小或下游慢导致池占用；
4. **下游限流**：自身资源全部空闲但 429/超时成比例 → 模型API/第三方配额，回到 Step 2 修正预测表。

## Step 8 — 输出：压测方案与报告

方案文档结构：
```markdown
# [项目] 容量验证方案 —— 目标 [X] QPS / P99 [Y]ms
## 1. 输入与假设（含环境折算过程）
## 2. 预测表（Step 2，压测后被证伪/证实）
## 3. 场景与脚本清单（S1~S5，含流量配比依据）
## 4. 观测面板与数据采集点
## 5. 执行阶梯与熔断线
## 6. 风险：对共享环境/线上数据的污染面（只读副本？影子表？禁写窗口？）
```
报告在方案骨架上追加：预测 vs 实测对照表、拐点归因证据（监控截图/火焰图结论）、
整改项按 `expert-review-meeting` 四级分类回填，并给出"下一档目标的前置条件"。

## 纪律红线

- 禁止在生产数据库上直接压写路径（影子表/克隆库/禁写窗口三选一）；
- 禁止无预测表开压；禁止只报"扛住了/没扛住"不给 P50/P95/P99 三线与错误率曲线的结论；
- 压测机指标与业务指标同板呈现，先自证清白（压测机不是瓶颈）再谈被测系统容量；
- 每份报告的最终答复必须回到一个问题：**目标档位下的安全水位是多少，第一断裂组件是哪个。**
